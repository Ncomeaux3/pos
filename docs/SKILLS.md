# Skill Tree: How It Works

The full Skill Tree spec, written by the owner on 2026-09-15 and stored here verbatim apart from the house rules (no em dashes, arrows spelled out) and the corrections listed under Amendments. The build plan is docs/plans/skills-v2.md; the decisions behind the amendments are in decisions/log.md under 2026-09-15. Where this file and an amendment disagree, the amendment wins.

## Amendments (2026-09-15, from the planning interview)

- **Event names.** Section 8 uses the names the code emits: `goal_reached` (not `goal_achieved`), `meal_cooked` (not `recipe_cooked`), `transaction_categorised`. `milestone_achieved`, `skill_taught` and `system_built` are not listed until something emits them.
- **XP source.** `modules/skills/xp.yaml` is the single source of `skills.xp_weight`. Module migrations that seeded their own rows are history; a migration truncates and reseeds.
- **Old ids.** Existing `core.skill_links` rows on the old tree are remapped to the closest new leaf in a migration, then existing events are backfilled into `core.event_skill_links` from the remapped links. History shows the new names.
- **Late links.** An XP-bearing event whose entity has no accepted link at emit time stores no snapshot rows. The first real placement (nightly model pass, `skills.link`, `skills.reassign` or `skills.resolve_unclassified`) writes the snapshot for that entity's snapshot-less events. A first write is not a rewrite; after it the rows are immutable.
- **Projects (section 15).** `primary_skills[]` and `secondary_skills[]` are not columns. A project registers in `core.entities` and its skills are `core.skill_links` rows with weight 2 (primary) or 1 (secondary), set through the shared SkillPicker. Project completion is `tasks.project.completed_at`; status is derived from it and the existing `archived` flag.
- **Goal weights (section 14).** Goal skill links use the same weight 2 and 1 toggle. "Active goal" means a goal entity with no `goal_reached` event in `core.events`; the skills module does not read the goals schema, so an archived but unreached goal still counts. Known gap.
- **No-skill-needed defaults (section 21).** Entity types transaction, subscription, policy and record pass `skills: false` to `register()` and receive the `none` marker without queueing. The marker is a `core.skill_links` row with `skill_id = 'none'`, `confidence = 0`, `classified_by = 'none'`, written by the skills classifier, never by core.
- **Challenges and achievements (sections 16, 17).** `skills.challenge` and `skills.achievement` tables in the skills schema, no new module. Tools `skills.write_challenge`, `skills.complete_challenge`, `skills.write_achievement`.
- **Tools (section 22).** `get_skill`, `get_evidence` and `review_unclassified` are not built; the page reads `modules/skills/data.ts` and agents use core `query`. `resolve_unclassified` is built.
- **Digest (section 18).** Existing field names stay because four readers depend on them: `attributes[].skillId`, `gainedThisWeek` (the doc's `topSkillsThisWeek`), `stagnant[].idleDays`. New fields are added beside them. Stagnant threshold stays 60 days; goal pressure stays 30.
- **Screen (section 19).** Built from this doc in the current visual language, no prototype round.

---

The Skill Tree is the character sheet for the Personal OS.

It answers one core question:

> What is the owner becoming capable of doing?

Every module can create evidence of capability: tasks completed, projects shipped, goals achieved, workouts logged, books finished, trips completed, businesses launched, presentations given, meals cooked, systems built, and so on.

Entities are linked to one or more skills. Events generated by those entities award XP to those skills. XP rolls upward from leaf skills to categories, from categories to attributes, and finally into the owner's character level.

The Skill Tree is not a productivity score. XP represents evidence of learning, practice, execution, and accomplishment.

The hierarchy is:

`character > attribute > category > leaf skill`

The nine default attributes are:

1. Faith
2. Self-Mastery
3. Learning & Intelligence
4. Engineering & Technology
5. Business & Entrepreneurship
6. Communication
7. Leadership & Relationships
8. Health & Physical Capability
9. Life Capability

The tree is personalizable, but the committed default contains no personal data.

## 1. Where Things Live

| Piece | Location | Notes |
|---|---|---|
| Default tree | `modules/skills/skills.yaml` | Committed, generic, contains no personal data |
| Owner edits | `skills.override` | Rows layered over the default YAML |
| XP weights | `modules/skills/xp.yaml`, seeded into `skills.xp_weight` | Unknown event types award 0 XP |
| Entity to skill links | `core.skill_links` | Current semantic relationship between an entity and skills |
| Event to skill snapshot | `core.event_skill_links` | Immutable skill attribution captured when an XP-bearing event occurs |
| Events | `core.events` | Append-only event ledger |
| XP view | `skills.xp` | Derived from events and immutable event skill snapshots |
| Level function | `skills.level(int)` in SQL, `level()` in `modules/skills/xp.ts` | Same formula in both; tests must agree |
| Rules classifier | `modules/skills/classify.ts` | Deterministic first-pass classification |
| Model classifier | `modules/skills/jobs/reclassify.ts` | Nightly fallback for unresolved entities |
| Digest | `modules/skills/jobs/nightly-digest.ts` | Writes summary to `core.digests` |
| Screen | `modules/skills/ui/` | Constellation, charts, details, edits |

The merged tree is constructed from `skills.yaml + skills.override`.

Parent pointers define the tree.

Roll-ups happen in TypeScript.

The database does not materialize category or attribute XP.

## 2. Design Philosophy

The system distinguishes between:

- **Identity**: who the owner is becoming
- **Goals**: outcomes the owner wants
- **Projects**: bounded efforts that move goals forward
- **Tasks**: concrete actions
- **Habits**: repeated behaviors
- **Skills**: capabilities that improve through evidence
- **Challenges**: deliberate tests of capability
- **Achievements**: meaningful milestones that permanently document capability

Goals, projects, tasks, and habits are not skills.

For example:

```text
Goal
  Build a profitable business
    Project: Validate the problem
      Task: Interview customer
      Task: Analyze interview notes
    Project: Build MVP
      Task: Build prototype
    Project: Get first customer
      Task: Conduct sales call
```

Those actions may generate evidence for:

```text
Customer Research
Sales
Speaking
Listening
Product Development
Coding
AI Engineering
Entrepreneurship
```

The Skill Tree therefore measures capability developed while pursuing real life, rather than creating a second checklist of things to grind.

## 3. The Tree

There are exactly three tree levels:

```text
attribute
  category
    leaf skill
```

Only leaf skills receive direct entity links and direct XP.

Categories and attributes are roll-up nodes.

Every node has:

- `id`
- `name`
- optional `parent`
- optional `description`
- optional `keywords`
- optional `aliases`
- optional `meta`
- optional `is_meta_skill`

Only leaf skills may define classification keywords.

A leaf skill has one canonical parent but may conceptually support multiple areas of life.

Do not duplicate a skill just because it applies in multiple domains.

Example:

`Negotiation` lives under Communication but may receive XP from business deals, compensation discussions, purchases, vendor conversations, or conflict resolution.

## 3.2 Meta Skills

Some leaf skills have unusually broad effects across the whole system.

They receive:

```yaml
is_meta_skill: true
```

Default meta skills:

- Systems Thinking
- Problem Solving
- Critical Thinking
- Learning How to Learn
- Decision Making
- Discipline
- Clear Writing
- Public Speaking
- Listening
- Leadership
- Adaptability
- Resourcefulness

Meta skills are not additional parents and do not create duplicate XP.

They are a UI and reporting concept only.

The UI may visually distinguish them because improvement in these capabilities tends to improve performance across many domains.

## 3.3 Editing the Tree

`skills.yaml` is never edited at runtime.

Every owner change is represented by a row in `skills.override`.

Kinds:

- `custom`: adds a new node
- `rename`: renames a default node
- `delete`: hides a node and its descendants
- `patch`: changes editable metadata such as description, keywords, aliases, or `is_meta_skill`

A custom node must respect the three-level hierarchy.

Deleting a parent hides all descendants so the merged tree never contains orphans.

`skills.restore(skill_id)` removes overrides for one node.

`skills.restore()` removes all overrides and returns the tree to the committed default.

Deleting or renaming a skill never destroys historical XP attribution.

Historical event snapshots retain the skill ID and display-name snapshot that existed when the event occurred.

## 4. Linking Entities to Skills

Classification determines what capabilities an entity is associated with.

Classification and XP are related but intentionally separate.

An entity may have current skill links:

```text
core.skill_links
```

An XP-bearing event captures an immutable snapshot of those links in:

```text
core.event_skill_links
```

This prevents future reclassification from rewriting history.

Example:

A task is originally linked to `Python`.

The task is completed.

The completion event snapshots `Python`.

Three months later the task is manually reclassified to `AI Automation`.

The historical completion still awards XP to `Python`.

Future events from the entity may use the new classification.

---

## 4.1 Step 1: Register

Every module calls:

```ts
core/entities.register()
```

`register()`:

1. upserts `core.entities`
2. invokes any registered classifiers
3. writes entity skill links
4. emits the entity event

The skills module declares itself as a classifier.

Deleting the skills module must leave the rest of the application operational.

---

## 4.2 Step 2: Rules

Rules execute synchronously before any model classification.

```ts
matchByRules(text, nodes)
```

Rules inspect:

- title
- body
- structured searchable fields supplied by the module

Matching is:

- case insensitive
- based on word boundaries
- alias-aware
- leaf-only

A rule hit writes:

```text
core.skill_links
confidence = 1
classified_by = 'rule'
is_manual = false
```

Multiple leaf skills may match one entity.

Rules should favor precision over recall.

A generic word should not be added as a keyword if it creates frequent false positives.

Examples:

Good:

```text
"python"
"fastapi"
"strength training"
"customer interview"
```

Bad:

```text
"work"
"run"
"plan"
"business"
```

---

## 4.3 Unclassified

If rules produce no sufficiently useful classification, the entity receives the special parking link:

```text
skill_id = 'unclassified'
confidence = 0
classified_by = 'unclassified'
```

`unclassified` is not part of the skill hierarchy and never earns XP.

It is a visible queue for unresolved entities.

A miss must never be silent.

---

## 4.4 Step 3: Model Classification

`jobs/reclassify.ts` collects unresolved entities nightly.

The classifier receives:

- entity type
- title
- body / searchable summary
- flat list of leaf skills
- skill descriptions where available

Batch size:

```text
20 entities
```

Maximum:

```text
10 batches/night
```

The model returns zero or more:

```json
{
  "skillId": "...",
  "confidence": 0.87
}
```

Only classifications above the configured acceptance threshold are applied.

Default:

```text
MODEL_ACCEPT_THRESHOLD = 0.70
```

Accepted links receive:

```text
classified_by = 'model:<model-id>'
is_manual = false
```

The `unclassified` marker is removed once at least one accepted link exists.

If the model:

- times out
- hits the spend cap
- returns malformed output
- returns no sufficiently confident match

nothing fails.

The entity remains unresolved for a future pass.

---

## 4.5 Confidence Is Classification Metadata, Not XP

Classification confidence must **not** reduce earned XP.

This is important.

A skill link is either accepted for XP attribution or it is not.

Do not calculate:

```text
event XP x classifier confidence
```

A model classification at `0.71` is not evidence that the owner performed only 71% of the work.

Confidence describes uncertainty in the classifier, not magnitude of accomplishment.

Therefore:

```text
confidence
```

is used for:

- auditing
- filtering
- model acceptance
- UI display
- review queues

It is not an XP multiplier.

## 5. Manual Skill Links

`core.skill_links.is_manual` is the override flag.

Manual classifications always win over automated classification.

Tools:

```text
skills.link(entity_ref, skill_id)
skills.unlink(entity_ref, skill_id)
skills.reassign(entity_ref, from_skill_id, to_skill_id)
```

Manual links use:

```text
is_manual = true
classified_by = 'human'
confidence = 1
```

Automated jobs must never overwrite a manual link.

Removing a manual link does not automatically restore an old model link.

The entity can be reclassified on the next classifier pass if it has no remaining valid links.

Every entity drawer uses the shared:

```text
SkillPicker
```

Display:

- skill name
- RULE / MODEL / HUMAN badge
- confidence where relevant
- remove control
- add skill control

The owner must always be able to correct the system.

## 6. Event Skill Snapshots

This is the canonical source for historical XP attribution.

When an XP-bearing event is emitted, current accepted entity skill links are copied into:

```text
core.event_skill_links
```

Suggested fields:

```text
event_id
skill_id
skill_name_snapshot
weight
source_link_id
classified_by_snapshot
created_at
```

This table is append-only.

An event's skill attribution never changes after creation unless an explicit administrative correction tool is used.

Normal entity reclassification must not rewrite historical XP.

This gives the system two concepts:

```text
core.skill_links
= what this entity is associated with now

core.event_skill_links
= what this historical event awarded XP to
```

## 7. XP Philosophy

XP should reward increasingly strong evidence.

The rough evidence hierarchy, weakest first:

1. Exposure
2. Learning
3. Practice
4. Execution
5. Completion
6. Outcome
7. Mastery / Teaching

Watching a video about sales should award far less XP than conducting a sales call.

Conducting a sales call should award less than closing a customer.

Closing one customer should award less than building a repeatable sales process.

The system therefore rewards application more heavily than consumption.

## 8. XP Weights

`modules/skills/xp.yaml` defines XP for recognized event types.

Unknown events award:

```text
0 XP
```

This is intentional so new modules cannot accidentally inflate the Skill Tree.

Defaults (event names as the code emits them):

| Evidence | Event type | XP |
|---|---|---:|
| Exposure | `article_read` | 2 |
| Exposure | `note_created` | 1 |
| Practice | `task_completed` | 5 |
| Practice | `workout_logged` | 5 |
| Practice | `meal_cooked` | 3 |
| Practice | `goal_checkin` | 3 |
| Learning | `idea_researched` | 5 |
| Learning | `book_finished` | 25 |
| Execution | `challenge_completed` | 25 |
| Execution | `trip_completed` | 20 |
| Outcome | `project_completed` | 75 |
| Outcome | `goal_reached` | 100 |
| Outcome | `achievement_unlocked` | 5 |

Not listed until something emits them: `milestone_achieved`, `skill_taught`, `system_built`.

Zero-XP examples:

```text
transaction_categorised
entity_created
task_created
note_updated
goal_created
```

Creating an intention is not capability evidence.

Doing the work is.

XP values are intentionally coarse.

## 9. Multi-Skill XP

One event may contribute to multiple skills.

To prevent XP inflation, the event has one XP budget which is distributed across its attached skills.

`core.event_skill_links.weight` defines the allocation.

Before snapshot creation, weights are normalized:

```text
normalized_weight(skill)
=
skill_weight / sum(all skill weights for event)
```

Therefore:

```text
sum(skill XP awarded by event) = event XP
```

Example:

A 100 XP project is linked to:

```text
Python               weight 2
AI Agents            weight 2
Product Development  weight 1
```

Normalized:

```text
Python               40 XP
AI Agents            40 XP
Product Development  20 XP
```

The project creates 100 total character XP, not 300.

Manual UI may allow the owner to adjust weights.

Default weights are `1`.

---

## 10. XP per Skill

`skills.xp` derives XP from:

```text
core.events
JOIN core.event_skill_links
JOIN skills.xp_weight
```

Formula:

```text
xp(skill)
=
sum(
  xp_weight[event.event_type]
  x event_skill_link.normalized_weight
)
```

The view should expose:

```text
skill_id
xp
event_count
last_event_at
xp_7d
xp_30d
xp_365d
```

Classification confidence is not part of the formula.

---

## 11. Levels

Level remains intentionally coarse.

```text
level = min(99, floor(sqrt(xp / 100)))
```

Examples:

```text
100 XP    = level 1
400 XP    = level 2
900 XP    = level 3
2,500 XP  = level 5
10,000 XP = level 10
```

The exact same function exists in:

```text
modules/skills/xp.ts
skills.level()
```

Automated tests verify that the implementations agree.

A level is an ordinal summary of demonstrated activity and evidence.

It must not be presented as scientific measurement of competence.

---

## 12. Roll-Up

Leaf skills receive direct XP.

Categories receive:

```text
sum(descendant leaf XP)
```

Attributes receive:

```text
sum(descendant leaf XP)
```

Character XP is:

```text
sum(all leaf XP)
```

Character level is:

```text
level(character XP)
```

Each event contributes to character XP exactly once because event XP is distributed rather than duplicated across linked skills.

This avoids multi-skill events artificially inflating the character level.

## 13. Capability Evidence

XP answers:

> How much evidence has accumulated?

It does not fully answer:

> How good is the owner?

Where useful, skill detail views may also surface evidence by type:

```text
Learned
Practiced
Completed
Shipped
Achieved
Taught
```

Example:

```text
Python, Level 4

XP: 1,780

Evidence
- 3 projects shipped
- 42 tasks completed
- 1 system built
- 2 books/courses completed
```

This is more meaningful than a level alone.

Do not invent a hidden "mastery score."

Show real evidence instead.

## 14. Goals and Goal Pressure

Goals may link directly to leaf skills.

A goal-skill relationship describes:

> Which capabilities matter for accomplishing this goal?

Goal skill links have:

```text
skill_id
weight
```

Goal weights are independent from classifier confidence.

A skill is under goal pressure when:

1. at least one active goal links to the skill
2. the weighted goal importance exceeds zero
3. the skill received zero XP in the configured inactivity period

Default inactivity period:

```text
30 days
```

`goalPressure(skill)`:

```text
sum(active goal skill weights)
```

A skill with no linked active goals is never under goal pressure.

It may still be stagnant.

---

## 15. Projects and Skill Development

Projects should be treated as one of the strongest sources of capability evidence.

A project may explicitly declare primary and secondary skills (see Amendments: link weights 2 and 1).

These do not replace classification of its child tasks.

They communicate intent:

> Which capabilities is this project supposed to develop?

At project completion, the `project_completed` event awards XP using the project's explicit skill links.

Tasks inside the project still award their own task XP independently.

This intentionally rewards both:

- repeated execution during the project
- the larger accomplishment of finishing something that exists afterward

## 16. Challenges

Challenges are deliberate tests of capability.

Examples:

```text
Give a public presentation
Run a 10K
Cold-call 20 businesses
Build an app in a weekend
Lead an event
Earn first business revenue
Cook dinner for 10 people
```

Challenges live outside the skill hierarchy.

They link to one or more skills.

Completion emits:

```text
challenge_completed
```

Challenges should generally award more XP than routine tasks because they represent deliberate capability tests.

---

## 17. Achievements

Achievements are permanent markers of meaningful capability or life milestones.

Examples:

```text
First paying customer
First $1,000 in business revenue
First employee hired
First software product shipped
First public talk
First 10K completed
First Bible study taught
First international solo trip
```

Achievements are primarily historical records.

They do not need large XP awards.

An achievement may optionally emit:

```text
achievement_unlocked
```

with a modest XP weight or zero XP.

The achievement itself is the reward.

## 18. Nightly Digest

`jobs/nightly-digest.ts` writes to:

```text
core.digests
```

The rest of the app consumes the digest rather than querying the skills schema directly for summary information.

Digest fields:

```text
attributes
totalXp
characterLevel
xpThisWeek
gainedThisWeek
gaining
stagnant
underGoalPressure
recentAchievements
recentChallenges
```

### `attributes`

For every top-level attribute:

```text
skillId
name
xp
level
xp30d
```

### `gaining`

Top 5 leaf skills by XP gained over the last 30 days.

### `stagnant`

Up to 5 skills that:

- have historical XP
- received 0 XP during the inactivity threshold (60 days)

Sorted by:

```text
highest historical XP
then longest idle period
```

This surfaces developed skills that are no longer being exercised.

### `underGoalPressure`

Leaf skills that:

- are linked to active goals
- have positive goal weight
- gained 0 XP during the previous 30 days

Sorted by goal pressure descending.

### `gainedThisWeek`

Top 3 leaf skills by XP earned this week.

### `recentAchievements`

Recent unlocked achievements.

### `recentChallenges`

Recently completed challenges.

## 21. Unclassified Review

The Skill Tree screen exposes the unresolved classification queue.

Each item shows:

```text
entity type
title
created date
model attempts
suggested skill if available
confidence if available
```

Actions:

```text
assign
ignore
mark no-skill-needed
```

`no-skill-needed` is distinct from `unclassified`.

Some entities legitimately should not award or map to skills.

Examples:

```text
insurance policy record
receipt
reference-only note
utility bill
passive transaction
```

Those entities can be marked:

```text
classified_by = 'none'
```

They disappear from the unresolved queue and earn no skill XP.

## 22. Tools (`skills.*`)

| Tool | Guarded | What it does |
|---|---:|---|
| `get_digest` | no | Returns the nightly Skill Tree digest |
| `write` | no | Add, rename, delete, or patch a skill |
| `restore` | no | Drop overrides for one node or all nodes |
| `link` | no | Add a manual entity to skill link, optional weight 1 or 2 |
| `unlink` | no | Remove an entity to skill link |
| `reassign` | no | Move a current entity link to another skill |
| `resolve_unclassified` | no | Human assignment or no-skill-needed |
| `write_challenge` | no | Create or edit a challenge |
| `complete_challenge` | no | Mark a challenge done; emits `challenge_completed` |
| `write_achievement` | no | Record an achievement; emits `achievement_unlocked` |

Historical event attribution is not modified by normal `link`, `unlink`, or `reassign`.

An explicit administrative correction mechanism should be separate if ever implemented.

## 23. Invariants

1. Rules always run before model classification.
2. Rules are deterministic and free.
3. Model classification happens asynchronously and in batches.
4. Only leaf skills receive direct entity links and direct XP.
5. Categories and attributes are roll-up only.
6. Every automated entity skill link stores `confidence` and `classified_by`.
7. Every manual link stores:
   ```text
   confidence = 1
   classified_by = 'human'
   is_manual = true
   ```
8. Manual links are never overwritten by automated classifiers.
9. Classifier confidence never scales XP.
10. Historical XP attribution comes from immutable `core.event_skill_links`, not the entity's current links.
11. Reclassifying an entity does not rewrite historical XP.
12. One event has one XP budget. Linking it to multiple skills distributes the XP rather than duplicating it.
13. Unknown event types award 0 XP.
14. Creating an entity alone should normally award 0 XP.
15. Application and outcomes award substantially more XP than passive consumption.
16. `unclassified` is a workflow state, not a skill.
17. `no-skill-needed` is valid and prevents meaningless classifications.
18. The default tree contains no personal information.
19. Runtime tree edits live entirely in overrides.
20. Removing the skills module leaves the rest of the app operational.
21. XP and levels are descriptive signals, not scientific measurements of ability.
22. Real evidence should always be inspectable behind a level.

## 24. Character Philosophy

The Skill Tree is designed around the following target:

> Become a confident, capable, faithful individual who can build and lead successful businesses, solve difficult problems, provide for and invest in the people around him, remain physically capable, understand the world, communicate clearly, build strong relationships, and continually develop the skills required to handle unfamiliar situations.

The tree should therefore favor capabilities that increase:

```text
agency
competence
wisdom
resourcefulness
adaptability
leadership
physical capability
communication
stewardship
```

These are outcomes of skill development, not XP categories themselves.

There is no direct:

```text
Confidence XP
Wisdom XP
Agency XP
```

Confidence should emerge from accumulated evidence of real capability.

## 25. Known Gaps / Future Work

- No historical import is required for initial launch.
- Existing entities may be classified incrementally as their modules import or touch them.
- Skill prerequisites are not modeled yet.
- Cross-skill dependency graphs are not modeled yet.
- Certifications and formal credentials are not modeled separately yet.
- Achievements and challenges are tables in the skills schema (see Amendments).
- Explicit evidence types may later allow richer skill profiles without changing XP.
- Skill decay is intentionally not implemented. The UI may show inactivity, but historical capability evidence is never destroyed.
- Category placement is intentionally canonical even when a skill affects several areas.
- The current system measures demonstrated activity better than absolute real-world mastery; it should make that limitation clear.
