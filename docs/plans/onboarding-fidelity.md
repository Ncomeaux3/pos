# Onboarding to the artboard

Superseded for styling on 2026-09-19 by the Holon redesign (docs/plans/holon-product-redesign.md, section 4): colour, type, radii, surfaces and control shapes now come from the Holon design contract and the shared components in `components/pos/`. This plan still governs what each screen shows and how it is laid out.


## Context

Core screen of the fidelity pass (method: docs/plans/weekly-review-fidelity.md). `POS Onboarding.dc.html` (619 lines, the artboard is large) captured at 1440x900 into `/private/tmp/pos-handoff-sources/onboarding/`: You, Modules, Connections (default, mid-search, a category open), Goals (default and with a third goal opened), Notifications, First run, dark and light (18 PNGs). The single biggest gap is not on the artboard at all: the app renders the full `PosSidebar` app nav around the wizard (`e2e/__screens__/onboarding-1440-dark.png` shows Dashboard, Finance, Skill Tree ... Settings down the left edge, plus the wizard's own step rail beside it), because the route lives under `app/(app)/` and `app/(app)/layout.tsx` renders `<Sidebar>` unconditionally. The artboard has no app chrome at all: just the wizard's own 300px rail and the question column, full bleed. That file is out of this pass's scope. Past that, the six steps are already close in structure (the app already has all six, in the same order, each saving as it goes rather than waiting for a submit) but thinner in content: no day-start picker, a flatter Connections step with no search, no top-5/more split, no manual add and no "needed" badge, and Goals with three fixed, uneditable starter goals against the artboard's five with per-goal target, due date and a check-in cadence that no schema field backs. The app also has one thing the artboard does not draw: a "You are set up" confirmation screen after Finish, standing in for the artboard's fake `window.location.href` jump to a dashboard that, in the app, is a real page it can actually link to.

Decisions with Nick (append to `decisions/log.md`):
- The doubled rail: `app/(app)/layout.tsx` renders `Sidebar` and `MobileTabBar` around every route under `(app)`, including `/onboarding`, so the wizard's own step rail sits inside the app shell rather than replacing it as the artboard has it. Fixing this needs either a conditional in that layout or moving the route out of the `(app)` group, both outside `app/(onboarding)/onboarding/**`. Default: leave the app shell in place (a fresh install's sidebar is mostly empty tiles anyway, and it lets someone reach Settings mid-wizard) and treat this pass's job as fitting the wizard's own content, not its frame. Alternative: exempt `/onboarding` from `Sidebar`/`MobileTabBar` in `app/(app)/layout.tsx` (core layout, Blocked for this pass).
- Step one's "WHEN DOES YOUR DAY START" picker (four preset times, logic line 545 to 546) has no backing setting: the app's actual "when the day starts" answer is `digest_morning_at`, already asked in step five, Notifications. Building a second, disconnected "day start" would either duplicate that setting under a different name or sit unused. Default: drop the picker from step one; keep name and timezone only, and let step five's existing digest time field carry the "day start" idea it already covers honestly. Alternative: keep a day-start control in step one and have it write `digest_morning_at` directly, moving that field out of step five (a bigger reshuffle of the Notifications step for one field).
- Per-goal editing: the artboard lets you type a TARGET and pick a BY WHEN date per selected goal (logic line 571, 576 to 577), plus a CHECK IN cadence (weekly, monthly, quarterly) that nothing in `goals.write`'s schema stores. Default: add TARGET (feeds `target_value`, parsed as a number, defaulting to the current starter value if it does not parse) and BY WHEN (feeds `deadline`, defaulting to the existing one-year-out calculation) as inline fields on a picked goal, wired to the same `GoalSeed` fields `seedGoals` already sends; drop the cadence buttons entirely rather than storing a value the goal never reads. Alternative: keep goals fixed as today (no per-goal inputs at all), the smaller diff.
- The artboard's five starter goals (logic line 355 to 361) include two written for the artboard author's own life: "Ship POS v1" (a specific project) and "Sub-24 minute 5K" (a specific runner's target), which is exactly what CLAUDE.md's "the code holds nothing personal" rule exists to keep out of a fork-and-fill template. Default: keep the app's own three generic seeds (six months of runway, clear the week every week, read twelve books) rather than porting the artboard's five. Alternative: add a fourth generic seed in the same spirit as "Ship POS v1" (a computed, generic project-completion goal) if Nick wants a fourth option; do not add the personal two as written.
- The Connections step's "Connected" panel (logic line 119 to 132) shows a spinner and "Backfills 90 days on the first run" as if picking a provider starts a live sync. It never does: `requestProvider()` only ever writes `status = 'requested'`; the real connection, and any backfill, happens later at Settings (as the step's own note already says). "90 days" is also only true for one provider family (`FIRST_RUN_DAYS = 90` in `modules/finance/jobs/sync-simplefin.ts`; Strava backfills a year on a first run). Default: no spinner, no "Connected" language, no backfill promise anywhere in this step; a picked provider reads "Requested" and sits in a plain list the same toggle removes it from, matching what `requestProvider`/`removeProvider` actually do. Alternative: none honest; a live-connecting affordance cannot be built without either a real inline OAuth flow (a bigger integration change) or a lie.
- The artboard's Connections step is grouped, searched and paginated (a global search across every provider, each category showing its top 5 with the rest behind a "more providers" select, plus a manual add). The app's `config/connectors.yaml` is a flat `providers: string[]` per category with 5 to 14 entries and no split. Default: keep one flat list per category (already true and already committed config) rendered as a wrapped button row exactly as today, add the global search across all categories' providers (a client-side filter over data the page already has, no schema change), and add the manual "Add a name" input per category (already just a `requestProvider(provider, categoryId)` call with a typed string) since both are pure UI work over data and actions that already exist. Do not build the top-5/more split; the app's lists are already short enough that showing all of them is fine. Alternative: also add the split now for parity with the artboard's exact interaction, more component work for no honesty gain.
- The artboard has a "Calendar & email" category (id `cal`, feeding `tasks`) that `config/connectors.yaml` does not carry, and a `needed: true` flag on two Finance categories (banks, brokerages) that the yaml has no field for at all. Default: add `needed?: boolean` to the `Category` type and the yaml (bank and broker), so the step can show the artboard's "carry the numbers behind Finance and Goals" note honestly; skip the Calendar & email category, since Tasks has no calendar integration and nothing reads that connection. Alternative: add the category anyway as a pure wishlist entry (like every unsupported provider already is), if Nick wants it listed even though nothing consumes it.
- The Ready step's `firstRunLine` (logic line 601) claims the nightly agent "pulls {n} sources, backfills 90 days" where n is however many were requested, none of which are real connections yet, and names 04:00 as a fixed hour the way the Review pass's cron fact already shows is only true in Chicago summer. Default: rewrite to name what tonight's run actually does regardless of requests: writes each enabled module's digest and sends one email, at the digest hour computed the same way the Review pass computes it (`clockIn(Date.UTC(y, m, d, 9), settings.timezone)` from `core/today`); drop "pulls N sources" and "backfills 90 days" since neither happens until a real connection exists.
