# Agent log to the artboard

Superseded for styling on 2026-09-19 by the Holon redesign (docs/plans/holon-product-redesign.md, section 4): colour, type, radii, surfaces and control shapes now come from the Holon design contract and the shared components in `components/pos/`. This plan still governs what each screen shows and how it is laid out.


## Context

Core screen (method: docs/plans/weekly-review-fidelity.md, scope rule from docs/plans/review-fidelity.md). `POS Agent Log.dc.html` captured at 1440x900 into `/private/tmp/pos-handoff-sources/agent-log/`: default (7 Sep run open), the Skills filter selected, an entry undone, and a failed job retried, each dark and light, 8 PNGs.

The screen was already built in Phase 1C (`core.write_log` with revert/apply payloads, `callTool` and `approve()` both logging, undo re-running the module's own tool) and the current app screens (`e2e/__screens__/agent-log*`) already match the artboard closely: same band shape, the same filter-pill row, the same run accordion with a mono date/clock/duration, the same 4-tile KPI strip, Jobs list, Undo history and Autonomy card, and Undo/Redo that genuinely reverts a write through `undoWrite()`. What differs is mostly copy punctuation and two controls the app never wired: the artboard's header carries "Undo last run" and a per-page theme button, and every failed job in the artboard's main list carries a "Retry now" button that the app's equivalent failed-job block does not. The app also draws two things the artboard does not: a "This run wrote nothing" line for an empty accordion, and a per-run "Undo this run" two-press control once a run is open with more than one reversible entry.

Decisions with Nick (append to `decisions/log.md`):
- The artboard's header carries a per-page theme toggle ("LIGHT"/"DARK", logic line 39). Not a decision: the 2026-09-11 Weekly Review decision already settled this for every header button, and 2026-09-12 repeated it for Health ("the sidebar's Dark row is the app's theme control... Rejected: a second theme button"). No change, no toggle added here either.
- The artboard's header also carries "Undo last run" (line 38), a single always-visible control that reverts every reversible write in the newest run. The app already has this at the run level: `UndoRun` inside the open accordion, a two-press "Undo this run" that appears once a run holds more than one reversible entry, and the newest run with writes opens by default. Default: no header duplicate; the existing per-run control is the only way to undo a run, reachable in one click since the relevant run is already open. Alternative: add a header shortcut that undoes the newest run without requiring it to be open first (a second entry point to the same two-press flow, `core/*` untouched either way).
- The artboard's failed-job block offers "Retry now" (logic line 266), turning into "Retry queued for tonight" after a click (lines 113, 266-267 in the demo's `retry`/`retryLabel`). The app's equivalent block (`RunLog.tsx`, the `r.jobs.filter(status === 'failed')` map) shows the raw error and "Retried twice inside the run, then left for the next one," with no button. `core/jobs.ts`'s `runNightly` already accepts `{ module }` to run one module's jobs alone, and its own comment says this is what Retry now is for. Default: build it for real, a new `retryModule(module)` action in `agent-log/actions.ts` calling `runNightly({ trigger: 'manual', module })` (no `core/*` edit, only a new caller), disabled and reading "Retrying" while pending, toast on completion the same way `RunNow` does. Copy differs from the artboard on purpose: the button always reads "Retry now" and never "queued", because this retry runs immediately in the request rather than waiting for a nightly slot, and it re-runs every job registered to that module, not only the failed one. Alternative: leave it out and keep today's read-only error block (a real but slower retry-from-the-dashboard-or-cron path already exists).
- The Jobs rail's names (line 224-233: "Bank + card sync", "Categorise + learn", "Task roll-forward", "Backup", …) are hand-written for the demo. No such jobs exist: real job names are `sync_simplefin`, `categorise`, `roll_forward`, `nightly_digest`, `pull_vault`, `embed`, `prune`, and so on (grep of every `modules/*/manifest.ts`), and several modules share the same name (`nightly_digest` alone is registered by nine modules), so the artboard's bare-name-no-module-prefix layout would read as nine identical rows. Default: keep the app's `{Module label} / {job.name}` shape (already correct) and humanise only the name half (`nightly_digest` → "Nightly digest"), never inventing per-job prose that does not exist in code. No core edit; a small formatter in `page.tsx`.
- Module colour on a write_log entry's tag (`MODC`, line 185): the artboard colours every module accent except Insurance (amber) and System (grey), with no stated rule (Finance's own FLAGGED entry, e2, is accent, not amber, so it is not "flagged rows are amber" either). The app has no signal that would generalise this (no per-module risk flag), so it is not chased: every real module's tag stays the single accent tone the app already uses, exactly as today.
